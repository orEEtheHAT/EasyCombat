# Снимки боевого состояния

`CombatSaveSystem` сохраняет значения боевых модулей в `CombatWorldSnapshot` либо JSON. Он не зависит от ES3, Яндекса, файловой системы или облачного SDK. JSON можно передать собственному хранилищу; этот пакет не выбирает транспорт и момент автосохранения.

## Подготовка

1. Создай `CombatDefinitionCatalog` через **EasyCombat → Saving → Create Definition Catalog**. Он собирает определения проекта и зависимости. ID состоит из GUID ассета и локального ID подобъекта; перенос ассета не ломает сохранение. Уже заданные ID кнопка обновления сохраняет.
2. Создай/найди игровые объекты и зарегистрируй каждый Health под постоянным ID экземпляра. Префаб врага и конкретный заспавненный враг — разные сущности: каждому экземпляру нужен свой ID.
3. Зарегистрируй источники статусов/формул и владельцев модификаторов. Корневой GameObject зарегистрированного Health добавляется автоматически. Для предмета, владеющего стат-модификатором, можно зарегистрировать обычный C#-объект под ID предмета.

```csharp
var registry = new CombatReferenceRegistry();
registry.RegisterActor("player", playerHealth);
registry.RegisterActor("enemy:room-4:spawn-2", enemyHealth);
registry.RegisterSource("item:sword:42", equippedSword);

if (CombatSaveSystem.TryCaptureJson(catalog, registry, out var json, out var error))
    storage.Write(json); // Ваш адаптер локального/облачного хранилища.
```

При загрузке сначала создай объекты с нужными компонентами и зарегистрируй те же ID, затем вызови:

```csharp
if (!CombatSaveSystem.TryRestoreJson(json, catalog, registry, out var restored, out var error))
    Debug.LogWarning(error);
```

Методы вызываются на главном потоке между боевыми операциями. Загрузка/сохранение из обработчика незавершённого удара или во время списания ресурса отклоняется. Для пула освобождай ID через `Unregister`, используй новый ID экземпляра и обычный `Health.ResetToFull()` при новом спавне.

## Что входит

| Модуль | Данные |
|---|---|
| Health | HP/max HP, Alive/Downed/Dead, ручная и временная неуязвимость, ссылки профилей |
| Защита | Значения каждого слоя: щит/заряды, максимумы, задержки/сроки, Enabled |
| Ресурсы | Текущие/максимальные значения, регенерация, начальная доля и оставшаяся задержка |
| Stats | Базовые значения, профиль, все группы модификаторов и ссылки владельцев |
| Статусы | Общие/независимые стаки, отдельные таймеры, просроченные тики, захваченная сила/формулы/лимиты, источники и происхождение |
| Способности | Заряды, кулдауны, общий кулдаун, незавершённая подготовка с оставшимся временем и целью |
| Buildup | Каждая шкала, задержка спада и кулдаун |
| Control | Ручные ограничения; ограничения статусов восстанавливаются со статусами |
| Реакции | Кулдауны владельца, других участников и корневых действий |
| Убийства | Вклад участников с относительным возрастом, признак уже выданной награды |
| Связи | Части тела/основное здоровье, guardian, профили модификаторов урона, команда |

Определения остаются SO: их содержимое не копируется в JSON. Каталог должен ссылаться на совместимую версию определений. Относительные таймеры не зависят от абсолютного Time.time новой сессии. Идентификаторы боевых жизней/действий переназначаются согласованно; старые объекты и новые источники после переиспользования пула не подменяют источники сохранённых эффектов.

Крит, шанс статуса и сила захваченных независимых стаков **не бросаются заново**. Восстанавливаются даже просроченные тики после большого шага: уже выполненные не повторяются. Живая SourceStat-формула читает нового восстановленного участника с тем же постоянным ID; исчезнувший/переиспользованный источник даёт нулевую живую базу, сохраняя ранее захваченные значения.

## Порядок загрузки и события

Сначала проверяются версия, ключ совместимости каталога, полный набор зарегистрированных акторов, состав модулей, ID определений, числовые значения и бюджеты. Затем готовятся новые состояния всех участников. Ошибка проверки не меняет персонажей и не останавливает действующие атаки.

После успешной проверки система завершает незавершённые доставки, применяет состояния всех Health, затем остальных модулей. Снаряды, лучи, взмахи и зоны не продолжают старую симуляцию; зоны прекращаются **без Exit-урона**. Их траектории, положение, геометрия и пуловые экземпляры не входят в снимок акторов. Возврат в пользовательские пулы через ICombatTransient/return callbacks должен выполнять очистку, не уничтожать зарегистрированных участников и не запускать новый gameplay при `CombatSaveSystem.IsRestoring`.

Во время применения отключены уведомления урона/лечения/смерти/возрождения, жизненного цикла статусов, реакций и списания ресурсов. После завершения приходят `Health.StateRestored`, уведомления изменения представления статусов/контроля и общий `CombatSaveSystem.Restored`. Они предназначены для обновления интерфейса и адаптеров. Уже выданные награды не повторяются. Обычный `Health.RestoreState` остаётся отдельным API для одного здоровья и не заменяет снимок мира.

Старые StatModifierHandle/ControlHandle не управляют новыми восстановленными приложениями. `CombatRestoreResult.Modifiers` и `Controls` сопоставляют прежние `SaveKey` новым handle. Владельцы стат-модификаторов из реестра сохраняются, поэтому `RemoveSource(item)` также продолжает работать.

## Границы и совместимость

Это формат **боевого состояния зарегистрированных участников**, а не сериализация всей Unity-сцены. Спавн/уничтожение акторов, их трансформы и общая активация, анимации, AI, инвентарь, ввод, выбор оружия и внешний игровой прогресс принадлежат игре. Компоненты и иерархия должны существовать до Restore; обычные Enabled/Active-флаги сцены должны быть подготовлены игровым загрузчиком. CombatBodyPart восстанавливает собственное поведение разрушения/коллайдеров и DisableObject по загруженному здоровью; Unity lifecycle при переключении объекта всё равно выполняется.

У всего снимка `Version=1`; HealthSnapshot внутри поддерживает версии 1 и 2. Неизвестные версии, другой CompatibilityKey и другой состав модулей требуют явной миграции DTO до Restore. DTO открыты и сериализуемы; хранение нового поля игры рядом с ними не требует изменения ядра. Наличие модулей и формул хранится явными флагами — это обходит особенность JsonUtility, который создаёт пустые вложенные объекты вместо null.

Бюджеты: до 4096 зарегистрированных Health, JSON до 16 Mi символов, внутренние ограничения модулей сохраняются. Сохранение/загрузка — операции с выделением памяти; их не следует выполнять каждый кадр. Загруженные данные проверяются, но JSON не защищает от читов и не заменяет проверку экономики на сервере.
